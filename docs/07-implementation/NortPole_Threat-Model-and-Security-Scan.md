# NortPole — threat model and security scan

Status: first version, 2026-11-12. **Written by the developer of the product (an AI assistant working with the owner), from what is built and checked in a sandbox. It is not an independent review, a penetration test or legal advice.** Each "control" below points to a check recorded in [REVIEW.md](../REVIEW.md); where no check exists the row says so.

## 1. What is being protected

| Asset | Why it matters |
| --- | --- |
| Documents a person may read, and the access rules around them | The product's central promise is that a draft only uses what its owner could open. |
| Drafts, approvals and what was sent | An approved draft can leave the workspace (web or email destination). |
| Credentials: model-provider keys, mail settings, signing keys, session secret | Theft lets an attacker use models, send mail, or sign packs. |
| The audit log and usage counters | The evidence of who did what. |
| Model routes and the data-class rules | They decide which data may reach a cloud model. |

## 2. Who might attack, and from where

An outsider reaching the web address; a signed-in person trying to read or send more than they may; a hostile **document** (a source or an uploaded file) that carries instructions for the model; a pack or plugin author; an administrator who is careless or compromised; a compromised dependency or image; the upstream project's servers (the product started from their code).

Trust boundaries: browser to proxy; proxy to web and API; API to database, cache and search index; API to model routes (local, private, cloud); API to send destinations; package signer to installer; the host to the internet.

## 3. Threats, controls and what is left

| # | Threat | Controls built (check) | Left open |
| --- | --- | --- | --- |
| T1 | A source tries to steer the model (override, leak, link, forged citation) | Source text neutralised and quoted as data; no tools on planning and drafting; citations kept only for sources the run had; a reviewer warning flag; owner approves the exact draft (injection suite and unit tests) | **Added later for workflow agents (A7 step 3): plan-then-execute.** The agent's plan holds only search steps within its limit, the person accepts it, and code runs exactly those steps; a database test with a hostile source asking for more searches and a send showed only the two accepted searches ran. **The 7B obeyed in 31% of runs on 25 hostile passages.** The model can still print text, add a link, repeat a false claim. The reviewer is the control. Only one small model measured. |
| T2 | Confidential data reaches a cloud model | Route kinds and data-class rules; unassigned route treated as cloud; refusal before any content is sent; redaction of listed patterns per route; audit of refusals (route and redaction tests) | Redaction catches listed patterns only (no names, addresses, free-text secrets); the data class is workspace-wide, not per document. |
| T3 | Someone reads a document they should not | Group-aware access lists; private-source rule; fail closed where unsure; access re-checked at send and when a draft is read (access tests on a real index) | Only synthetic data and one source type; no real connector with per-document sharing. |
| T4 | A draft changes after approval, or is sent to the wrong place | Approval names the draft's fingerprint; action fingerprint covers destination and payload; expiry and single use; tiers re-read at each step; send-time re-check (action tests) | **Added later: an optional second approver per destination.** When on, the owner's approval only moves the send to "waiting for a second person"; an administrator who is not the owner, and who could open every source the draft cites, must approve the same exact payload. The rule is read again at send time, so turning it on stops older approvals too (database tests, a browser run). Not built: a second approver for policy changes; approvers are administrators (no separate approver role); with one administrator who is also the owner, such a destination cannot be used; the approver reads the owner's draft, which is recorded in the audit log. |
| T5 | A destination used to reach internal systems (SSRF) | Address checked once and the connection pinned to it; link-local, metadata and reserved ranges refused; no redirects; certificates verified; recipients fixed by the administrator (delivery tests incl. a live TLS check) | The private-network range is allowed for the web destination (needed for local testing); an administrator can register an internal address. |
| T6 | A malicious or tampered pack | Signed packs, strict manifest, trusted-signer list, revocation, per-model evaluation, declarative-only rules, autonomy tiers (pack tests, runbook) | Signing keys are held by whoever signs; no hardware keys or expiry; no code in packs by design. |
| T7 | The audit log is changed or lost | Written for refusals, changes, sends and exports; privacy checks that it holds no draft text; retention with a floor and a legal hold; export is itself audited; **a hash chain (added later the same day)** links every new event to the one before, an administrator can check it, and a prune records where the surviving chain starts (unit tests, database tests, a live edit caught in a browser) | The chain catches an edited event and one removed from the middle. It does **not** catch removal of the newest events, or a rewrite of the whole chain by someone who can recompute every hash, unless the latest hash was kept somewhere they cannot reach: every event's log line carries it, so keep those logs off this machine. Events before the chain existed are not covered. **Added later: an off-box head.** `GET /admin/audit/head` gives the newest event's `id:hash`; `scripts/audit_head_snapshot.py save` (run from another machine) appends it to a file, and `check` (or `/admin/audit/verify?anchor=id:hash`, or the Compare box on the Audit log page) says whether that event is still there. Removal of the newest events then shows as "newer than the log". It only helps if the saved heads live where this machine's administrators cannot change them, and someone must run it on a schedule; nothing is scheduled here. |
| T8 | A compromised or careless administrator | Admin-only endpoints checked for signed-out and ordinary users; admin changes audited | One administrator can change policy, lift a hold, register destinations and place signers. **Added later: an optional two-administrator rule** for route policy changes and for retention and legal-hold changes (off by default; Governance page). With a rule on, a change is held until a different administrator approves it, is checked when proposed and again when applied (it is refused if the setting moved in the meantime), expires after 7 days, and is audited with both people; switching a rule off while any is on needs the second administrator too. Not covered: signer changes, send destinations, extension rules, user and group changes and other administrator actions; no admin MFA (single sign-on not built); anyone with direct database access can still change anything. |
| T9 | Secrets leak | Compose refuses to start without the session secret and database password; keys not in the repository; extension and MCP calls checked against an allowlist | Provider keys and mail credentials live in the database or environment, not a secrets manager; no rotation procedure for them. |
| T10 | The product calls the upstream project's servers | **Found and fixed in this pass:** release notes, price tables and recommended-model lists were fetched from the upstream GitHub repository by default (and would have shown upstream's release notes to users); `NORTPOLE_AIRGAPPED` now defaults on. Telemetry was already off by default | The web app can still reach analytics or error services if their keys are set; not exercised. |
| T11 | A vulnerable dependency | Scanned in this pass (section 4); 12 of 13 Python findings and the one high JavaScript finding fixed | 1 Python and 5 JavaScript findings remain (build tools or unused code paths); no vulnerability scan in CI. **Added later:** `tools/sbom/generate_sbom.py` writes a CycloneDX bill of materials from the two lock files (the CI workflow does this on every run and keeps it as a file), so a new advisory can be matched against what a release pins; it does not cover base-image packages. |
| T12 | One customer sees another's data | Single workspace by design | **Not multi-tenant.** Hosting several customers in one deployment is out of scope until designed. |
| T13 | Overload or abuse (denial of service) | Request-size limits in the proxy file; upstream rate limits unchanged | Not tested; no per-user quotas for model use; a malicious PDF could cost CPU (dependency fixed, unproven). |
| T14 | Weak sign-in | Basic email and password with the upstream's rules; first account becomes administrator | No single sign-on, no MFA, no recovery procedure written; the first-account rule is a risk on an exposed fresh install. |
| T15 | A compromised image or build | Images built from the lockfiles; no system packages in the API image; non-root user | Not signed; no software bill of materials; base images not pinned by digest; no scan of the built images. |
| T16 | Personal data kept too long or in the wrong place | Retention periods and a legal hold exist | Periods are placeholders; stored drafts and source snippets are not redacted; no per-person deletion or export. |
| T17 | A chat agent calls a tool that runs code or reaches an outside system, steered by a source or a page | **Added 2026-11-13: a tool catalog.** Every tool the core can give a chat agent has a kind; code (Python, the coding agent, code mode) and outside tools (MCP, OpenAPI, any unknown tool) are off by default and are never offered to the model while off; the check runs where the core builds a chat's tools and keeps only read tools if the check itself fails (unit and database tests, a live chat) | Web tools (search, open an address) stay on by default and can carry text out in an address; tools that are on run with no approval step in chat; MCP and OpenAPI tools now need their own approval, which pins a hash of their definition (name, description, schemas); a definition changed in storage, or found changed on its server by a check, is withheld until approved again, and saving other settings never re-approves it; each call is logged without arguments or results (A7 step 4); the check is only as fresh as the last time someone runs it, and a server can still behave differently from its description; deep research uses the same filtered tools; the Slack bot runs the same chat turn, so the same check should apply, but that was not tested; the coding agent's own sandbox tools are inside the coding agent and are governed only through it. |

## 4. Dependency and licence scan, 2026-11-12

Tools: `pip-audit` (PyPI advisories) on the 349 packages pinned by the lockfile's backend group; `bun audit` on the web lockfile; `pip-licenses` on the installed Python packages; `license-checker` on the web production tree. Advisory databases change daily; this is one snapshot.

**Python, before:** 13 known vulnerabilities in 4 packages. **Fixed** by raising pins: `pyasn1` 0.6.4 to 0.6.5 (4 findings, certificate and ASN.1 decoding), `pypdf` 6.21.2 to 6.21.4 (7 findings, crafted PDFs causing heavy memory or CPU), `oauthlib` 4.0.0 to 4.0.1 (1 finding). After the change a PDF reads and the OAuth client builds a request; the unit tests that cover these libraries could not be run here because they need a database engine. **Left:** `urwid` 2.6.16 (CVE-2026-103022, fix needs version 4): it comes in through `mitmproxy`, which the sandbox-proxy feature (Craft, not running here) imports for HTTP only; the product does not import urwid and the flaw is in urwid's web display. Accepted for now.

**Web, before:** 11 vulnerabilities (1 high, 6 moderate, 4 low). **Fixed** within version ranges: `source-map-js` (the high one; denial of service in a build tool), `fast-uri` and `qs`. **Left (5):** `glob`, `minimatch`, `postcss-selector-parser` (build and test tooling), `deepmerge`, `katex` (a low prototype-pollution issue in the maths renderer; a fix crosses a major version). A clean frozen install works with the new lockfile.

**Licences (revised the same day).** My first pass searched licence names for copyleft and source-available terms and **missed a proprietary one**: `azure-cognitiveservices-speech` 1.50.0, Microsoft's Speech SDK, is under Microsoft's own software licence terms (not open source; it limits use and redistribution and carries a binding-arbitration clause), and was installed by default for an optional Azure voice feature. It is now in an optional dependency group (`azure-voice`), not in the default install or the images; Azure voice needs `uv sync --group azure-voice` and acceptance of Microsoft's terms. A repeatable screen now exists: `tools/licenses/check_licenses.py` fails on AGPL, SSPL, BUSL, Commons Clause, non-commercial and proprietary licences, and on any package needing a decision (GPL, LGPL, MPL, unknown) that is not recorded with a reason in `tools/licenses/reviewed.json`; it passes on the 346 Python packages of the sandbox environment and the 71 web production packages, with 20 recorded decisions (six LGPL libraries used unmodified as installed libraries, three MPL ones, dual-licensed packages where the permissive option is relied on, and packages whose metadata is empty but whose own files carry a licence: Apache-2.0 for `agent-client-protocol` and `google-crc32c`, MIT for `voyageai`, `mitmproxy_rs` and `tiktoken`). Two remain unverified and are recorded as such: `zulip` (no licence in metadata or files; used only by an inherited connector) and `mitmproxy_linux` (no licence text; same project as the MIT `mitmproxy_rs`, which is an inference; sandbox-proxy feature only). `tools/licenses/generate_notices.py` writes a third-party notices file (about 1.8 MB for the Python set; generated, not committed): **21 packages ship no licence file** (including `dnspython`, `langchain-core`, `langsmith`, `onnxruntime`, `pypdfium2`, `tokenizers`, `markitdown`, `magika`, `ply`, `zulip`), so their notices have to be added by hand from the projects before a release. The web development tree was not scanned. This is a screen of package metadata and files, not legal advice, and a lawyer should review it before anything is distributed.

## 5. Findings changed in this pass
- Upstream fetches off by default (`NORTPOLE_AIRGAPPED` now defaults on; set it to `false` to allow them).
- Seven admin screen strings pointed to the upstream project's documentation or used its domain as an example; they now carry no upstream link (docs link removed, LiteLLM's own docs linked for the custom-provider help, example.com in placeholders). The remaining references to the upstream project (help links, code comments, tests, skills, the MCP client configuration template) were removed on 2026-11-14; see `services/core/UPSTREAM.md`.
- Dependency pins raised (section 4).

## 6. Not assessed
Penetration testing; the chat path and the upstream features this product inherits (the connectors, Craft, the Slack bot) beyond what is listed; mobile clients; physical and organisational controls; backup and recovery; the behaviour of any cloud model; a review by someone who did not write the code.

## 7. Suggested next steps (not done)
A scheduled off-box save of the audit log's latest head (the chain and the head check are built, no schedule is set up); administrator MFA and single sign-on; a secrets manager; image signing; a vulnerability scan in CI; a two-administrator rule for the remaining administrator actions (signers, destinations, extension rules, users); an external review before any pilot with real data.
