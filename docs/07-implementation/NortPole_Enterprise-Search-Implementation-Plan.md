# NortPole Enterprise Search implementation plan

**Status** — Ready for engineering review. The first release delivers Knowledge search. Chats and Workflows follow in the same interface. The third release adds cited Chat handoff and search scopes for agents and packs. Product scope and pilot targets are in the [Enterprise Search PRD](../04-specs/NortPole_Enterprise-Search-PRD.md).

### Engineering notes

- **Reuse points.** Inspect the [existing search API](../../services/core/nortpole/server/features/search/api.py), [search models](../../services/core/nortpole/server/features/search/models.py), and [OpenSearch query builder](../../services/core/nortpole/document_index/opensearch/search.py). The raw endpoint currently limits results to ten sections and still initializes a default chat model. Give the workspace page a contract that supports stable document grouping, permissions, and pagination without changing how existing callers consume results.
- **Pagination.** Prototype with the existing hybrid candidate depth and compare how different settings affect unique-document recall and latency. Use a deterministic tie-break on stable document IDs. If the chosen retrieval strategy exposes a bounded ranked window, surface that limit in the response and verify continuation against that window. Never reuse a continuation as proof of access.
- **Trace handling.** Extend the [search tracing tests](../../services/core/tests/unit/nortpole/server/features/search/test_search_api_tracing.py) with the new path and an enabled exporter. Include pseudo-sensitive terms and excerpts in synthetic tests so accidental payload capture is detectable. Keep the diagnostic events needed to monitor timing and failure category.
- **Authorization and freshness.** Build on [source-access enforcement](../../services/core/tests/nortpole_integration/test_source_access_enforced.py) and [Drive permission sync tests](../../services/core/tests/nortpole_integration/test_drive_permission_sync.py). Record a separate freshness limit for permissions and document content per synced source. State which upstream changes take effect immediately and which depend on a successful sync. A source with incomplete enforcement, an unknown permission mode, or an unverified freshness limit stays outside the pilot.
- **Relevance assessment.** Extend the [retrieval quality tests](../../services/core/tests/nortpole_integration/test_retrieval_quality.py) with long documents, near-duplicates, exact identifiers, paraphrases, no-match cases, and different access profiles. Use the PRD’s top-three, top-five, and latency figures as starting hypotheses. Record the corpus and load profile before deciding production thresholds.

## Release 2 — Chats and Workflows

1. Add result providers for chat and workflow objects behind the shared Search page. Keep the query when switching tabs and maintain filters for each result type.
2. Search accessible conversation titles and messages. Return a stable conversation link and a message anchor when supported. Reuse navigation from the [chat search menu](../../apps/workspace/src/sections/sidebar/ChatSearchCommandMenu.tsx). Verify that older messages are reachable and deleted messages leave the results.
3. Search visible workflow definitions and authorized run metadata and outputs. Reuse [workflow run navigation](../../apps/workspace/src/sections/workflows/WorkflowRunsPage.tsx) and the owner-checked scheduled run routes. Check access separately for each run even when its workflow definition is shared.
4. Verify mixed-access scenarios, cross-tab navigation, and direct links to older records before enabling the tabs. An authorized coworker can find the shared workflow definition while its owner’s private run remains private.

## Release 3 — Cited Chat handoff

1. Let users select Knowledge results or a library and open Chat with the selected references visible. Pass stable IDs and the selected scope through the composer.
2. Resolve those references at execution under the current principal. Retrieve only accessible passages and cite each supporting source. If an item is revoked, deleted, or unavailable, return usable remaining evidence and describe any evidence gap without revealing restricted details.
3. Expose the scoped retrieval path to agents and packs. Let horizontal and vertical packs suggest library defaults within the user’s existing access.
4. Verify cited links, unsupported questions, revoked content, scope handling, and consistent retrieval permissions across Search and Chat. Evaluate cross-document comparison and live-source retrieval separately after this release.

## Draft implementation and review

- **Requirements and design.** Search now opens Knowledge in the workspace sidebar. The first slice covers workspace-managed library uploads, documents added through the ingestion API, and the caller’s indexed personal files. The page supports library, source, and updated-date filters. The existing chat search opens from the Search page.
- **Architecture.** The workspace endpoint calls existing OpenSearch retrieval directly. It uses hybrid retrieval with a keyword fallback and has no dependency on a default chat model. Ranked passages are grouped by document. A five-minute tenant-scoped Redis continuation stores ordered document IDs and a request fingerprint. Each request gets fresh candidates and checks current database permissions and library membership before returning any excerpt.
- **Privacy review.** Workspace search emits no query or excerpt trace spans. Slow OpenSearch logs record timing and phase data without the query body. Query embedding failures omit the request text. Search links to NortPole-hosted files ask for a fresh authorized response.
- **Verification.** The backend suite covers a 45-document case with tied scores and repeated passages, revocation between pages, continuation isolation, file cache behavior, and the real database access check for stale index candidates. Authenticated browser checks use the preview API for indexed results, filters, original files, and mobile layout. A simulated multi-page feed checks retry and reauthorization of restored results.
- **Rollout boundary.** The current candidate window is capped at 300 passages. Pilot relevance and load measurements are still pending. Synced connectors need verified permission freshness and enforcement before inclusion. The dedicated Chats and Workflows tabs and cited handoff are later releases.

### Chats and Workflows in the draft

- The Search page keeps one query across all three tabs and remembers each tab’s filters. Chat search matches titles and visible messages in the caller’s conversations. Message links load older pages and focus the match when it is on the active conversation branch.
- Workflow search covers schedule names, scheduled-run metadata, and terminal Expense Review and Document Review responses. Shared schedule definitions use the group rules from Scheduled Workflows. Only the owner can find a schedule’s private runs. Workflow type, status, and date filters apply at the query boundary.
- The activity endpoint uses full-text search and chronological continuation scoped to the caller and query. It applies current resource and token permissions on every request. The database and browser verification covered shared definitions, private runs, old message and run destinations, filters, and mobile layout.

### Cited Chat handoff in the draft

- Search gives users a choice of up to five result passages or the currently selected library. The new Chat composer shows removable chips and waits for the user to send a question.
- The handoff sends stable document and passage IDs or a library ID. Chat resolves the references again against the current user, token, agent and deployment scope. Sources that fail the access check do not enter the model context. If no evidence remains, Chat returns an error and the user can change the selection.
- The first evidence-grounded turn uses the existing Chat citation format and the original source links returned by Search authorization. Selected results resolve the chosen passage. A library search retrieves current relevant passages within that library.
- Browser checks verified both composer handoffs and confirmed that the send payload contains references without excerpts. The live chat API emitted a citation for a selected indexed passage. Automated checks covered inaccessible references, library membership, citation links, and existing selected-source behavior.

### Google Drive pilot

1. In **Admin Panel → Connectors → Google Drive**, authorize a connector account that can read the pilot folder and its permission list. Scope the connector to that folder and choose **Sync with Google Drive** under **Document Access**. Index the connector and add it to one Knowledge library.
2. Set `NORTPOLE_SEARCH_DRIVE_PILOT_LIBRARY_ID` to that library’s ID on the server. Set `NORTPOLE_SEARCH_DRIVE_PILOT_TENANT` if the tenant is different from `public`. The pilot needs an active permission-synced connector, a completed source-ID backfill with enforced access checks, and verified NortPole email addresses that match named Drive grants.
3. For the pilot, users choose the configured library in Search. NortPole checks current Drive file metadata and named user grants before returning a passage. Search-to-Chat checks again when the question is sent. Unconfirmed, expired, and revoked grants are withheld. Group, domain, and link-only grants are outside this pilot.
4. The pilot bounds live checks to 12 candidates per request and stops starting new checks after eight seconds. A fresh grant may need indexing before it becomes discoverable. The reader and non-reader test, revocation before Chat send, and provider failure are covered with test records and a simulated Drive service. Live Google verification requires an authorized connector and two pilot identities.
